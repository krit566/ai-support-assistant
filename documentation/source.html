Overview

HelpDesk AI is a support assistant that any team can set up on its own documents. A team uploads help articles, policies or FAQs (PDF, Markdown or text). Customers then ask questions on a public chat page; the assistant answers only from those documents, shows the exact passage each answer came from, and says "I could not find this" instead of guessing when the documents do not cover a question. The team sees what customers ask, what was refused, and which answers were rated unhelpful, which tells them what to write next.

Data model

erDiagram WORKSPACE ||--o{ USER : has WORKSPACE ||--o{ KNOWLEDGE_BASE : owns KNOWLEDGE_BASE ||--o{ DOCUMENT : contains DOCUMENT ||--o{ CHUNK : "split into" KNOWLEDGE_BASE ||--o{ API_KEY : "public keys" KNOWLEDGE_BASE ||--o{ CONVERSATION : receives CONVERSATION ||--o{ MESSAGE : contains MESSAGE ||--o| FEEDBACK : "rated by"
  • Documents keep their extracted text, so they can be re-chunked later without the original file; a re-upload with the same name increments version.
  • Messages store the cited passages (JSONB) as they were at answer time, so an old answer still shows its evidence after the document changes.
  • Chunks can store an embedding vector (float[]) for embedders that do not depend on the rest of the corpus; LSA vectors are recomputed at rebuild.
  • All foreign keys use ON DELETE CASCADE; deleting a knowledge base removes its documents, keys and conversations.

How a question is answered

flowchart TD Q[Question] --> R[Hybrid retrieval
BM25 + embeddings, Reciprocal Rank Fusion] R --> T{Best passage weak
on both signals?} T -- yes --> N[The knowledge base's 'not found' message
no model is called] T -- no --> G{LLM enabled?} G -- no --> E[Extractive: most informative sentences] G -- yes --> L[LLM answer from numbered passages] L --> V{Cites only the passages
it was given?} V -- no --> E V -- yes --> A[Answer + cited passages] E --> A
  1. BM25 scores exact words; rare words count more (IDF), repeats saturate (k1), long passages are not favoured (b).
  2. Embeddings score meaning; LSA (TF-IDF + truncated SVD) offline by default, plain TF-IDF for knowledge bases under 8 passages.
  3. Reciprocal Rank Fusion merges the two rankings by position, so their different score scales never need to be compared.
  4. Refuse rule: if the best passage is weak on both signals the assistant refuses with the knowledge base's own message.
  5. Answer: extractive by default; with an LLM configured, the reply must cite passage numbers it was given, or the extractive answer is used.

Engineering decisions

Index in memory, version in the database

Every document change increments knowledge_bases.index_version in the same transaction (as an SQL expression, so two concurrent uploads both count). Before answering, a process compares its cached version with the database's and rebuilds if they differ, which keeps several server processes consistent without a message bus.

Why not pgvector? BM25 needs word statistics over the whole knowledge base and LSA is fitted on all passages, so both are rebuilt from all passages anyway; for a few thousand passages that takes well under a second. pgvector would move nearest-neighbour search into the database for very large collections, but keyword search would still need a separate full-text index and the rankings would still be fused in the application.

Thresholds do not transfer between corpus sizes

The refuse thresholds were tuned on the 53-passage placement-cell corpus. The first product version refused every question on a small knowledge base: BM25 scores shrink with corpus size (a word found in 1 of 2 passages weighs 0.69, in 1 of 53 it weighs 3.58), so the tuned bar of 3.5 was unreachable. The BM25 threshold is now expressed in units of "one rare word" and converted for each knowledge base. On the placement corpus the conversion is exactly a no-op.

A test uploads the 20 evaluated articles through the API and checks that the product makes the same rankings and the same refuse decisions as the evaluated engine for all 46 evaluation questions, so the evaluation numbers describe the product.

Refusing is the weak spot. In the demo, "Which buses go to the city campus?" is answered with the off-campus offers article because "campus" matches, and "How do I raise a complaint about a recruiter?" is refused although a grievances article exists. The articles and questions were written by one person and the test set is small (one question ≈ 3 points), so all scores are optimistic. CI fails the build if recall@3 drops below 0.90.

Analytics and the feedback loop

  • Questions per day, answered vs refused, every day in the range including empty days.
  • Refusal rate, helpful rate, p50/p95 answer time (SQL percentile_cont; shown as "–" when nothing was timed).
  • Gaps: refused questions grouped by their most frequent informative word; each group is a candidate article.
  • Low-rated answers with the customer's question, comment and the passages that were cited.
The demo seed asks 16 sample questions through the real engine; their thumbs up/down are invented and the conversations are labelled "demo" in the UI.

The public page works with a publishable key created per knowledge base. The key is visible to visitors, so it can only ask questions of that one knowledge base, is stored only as a SHA-256 hash, can be revoked, and is rate-limited per key with a sliding 60-second window (429 with Retry-After).

Limitations and next steps

  • Refusal and sentence choice are the weak parts; next, evaluate pretrained embeddings and the LLM mode on the same split, and tune thresholds per knowledge base from thumbs-down data.
  • Rate limiter and index cache are per process; with several instances the limiter moves to Redis.
  • Uploads are parsed inside the request; large PDFs need a background job queue. No OCR for scanned PDFs.
  • The session token is kept in localStorage; an httpOnly cookie with CSRF protection is stronger for production.

Interview questions

Why fuse rankings with RRF instead of adding scores?
BM25 scores are unbounded and cosine similarities lie in [−1, 1]; adding them lets one dominate. RRF uses only positions.
Why did the thresholds need rescaling?
BM25's IDF depends on how many passages exist, so the same "one rare word" match scores 0.69 in a 2-passage knowledge base and 3.58 in a 53-passage one. A fixed threshold either refuses everything on small bases or nothing on large ones.
How does the cache stay correct with several server processes?
Each change bumps index_version in the same transaction; every process compares its cached version with the database before answering.
Why return 404 for another workspace's ids?
403 would confirm the id exists; 404 reveals nothing about other teams' data.
Why bcrypt for passwords but SHA-256 for API keys?
Passwords are short and guessable, so hashing must be slow; API keys are 24 random bytes, so a fast hash is already infeasible to reverse.
What still protects a knowledge base if its public key leaks?
The key can only ask questions of that one knowledge base, is rate-limited, and can be revoked without affecting other keys.
